## 背景与概念澄清

**领域方法论（用户给定，是需求本体，代码里读不到）**：自上而下的四层测试设计体系——

1. **业务链路层**：基于业务信息梳理拆分而来，可分 1 级 / 2 级……无大业务变化则链路基本不变，故**首次拆分必须完整、精准、颗粒度合适**。
2. **用户故事层**：链路的进一步细分。**只有子链路才有用户故事**。一个故事的测试点既涉 a 链路又涉 b 链路时，**a、b 链路下都可以有这个故事**——允许重复，**重复比遗漏好**，智能体不得自动去重，只能标注重复交人决定合并。
3. **测试点层**：故事的进一步细分。**测试点不是可选层**，每个故事理论上都应拆出测试点（用户原话「测试点（可选）作为索引树」的"可选"指要不要进索引树，不是该层可跳）。
4. **测试用例层**：在测试点基础上把设计转化为用例内容并按规范生成——**用例正文就是这个智能体写的**。

前三层作为用例的**索引树**维护进知识库，新需求来时用于判定"属于已有链路/故事"还是"需要新增"，最终靠增删改四层节点保证用例与产品业务完全对齐。

**两阶段工作模式（本专项骨架，勿按"逐枝走完四层"理解）**：
- **第一部分 测试设计 = 全局视角**：一次覆盖所有链路 / 所有故事 / 所有测试点，产出**覆盖度完整的增量测试大纲**，不分枝推进。
- **第二部分 用例编写 = 链路视角**：按大纲一条子链路一条子链路生成用例（第四层）。
- 本期只做**第一部分**（三层 + 大纲 + 回写）；第二部分留下一片。

**能力优先，不是产物优先**：本片建设的是"能生成测试设计的智能体能力"，不是某一份大纲。因此不允许拿"先只铺链路层"这类**产物切片**当范围裁剪（那是走查分期，不是能力范围）。

**产品线中立：本专项对知识库里的内容零感知**（2026-10-05 追加裁定）。建的是**面向所有产品线**的测试设计能力，任何一条产品线（包括本机当前那条）KB 里已经存了什么节点、有多少量、正文写成什么样，**都不进设计前提、不进判据、不进成本估算**。本文只对 KB 的**能力面**有前提（P-1~P-4：枚举、增改删、可寻址、新桶入索引），内容面一律不假设。运行期由智能体**按类型枚举自行探测**，探测结果是运行时输入而非设计输入。

**覆盖度无客观分母**（用户定死）：不接受 PRD 清单 / 存量平台对照 / 签字当分母。结论——设计层的穷尽性没有客观判据，只能靠**独立视角复审 + 人审签字**；**禁止把"AI 评审通过"当质量证据**（假绿）。

**业界标准形态对照**：Anthropic《Building Effective Agents》的 orchestrator-workers 与 evaluator-optimizer；LangGraph plan-and-execute + reflection(Reflexion)；Manus/Cursor 的"计划外置成账本文件"；Kiro spec-driven 的追溯矩阵。与 Qodo Cover 的关键差别：用例设计**没有客观反馈信号**，所以环的出口只能是"独立复审 + 意见全量消化到零（或轮次用尽）"+ 人类门，不能是自动打分。

## 用户裁定（2026-10-05，逐条确认）

1. **首期范围** = 测试设计三层 + 增量大纲 + 过审后回写；用例编写（第四层）留下一片。
2. **全局推进** = 分块依次生成 + **每层收口各一次全局审**。
3. **评审主体** = 三层各自**不设人审**，评审**全部由子智能体**完成（独立视角，不给自己盖章）；**整个循环唯一的人类门 = 三层做完生成的增量大纲**，位置在大纲定稿之后、回写知识库之前。
4. **优化归属** = **主智能体**（用户授权控制方判定）。理由：① 结构性动作（跨枝新增/移动/删除、补接缝节点）需要全局账本与父子引用一致性；② 单写者原则，改哪一条的决策不能散进 N 个子上下文；③ "独立"已由评审侧满足，优化再独立只剩重建上下文的成本。三条配套约束见 §5。
5. **每层工作流**（用户原话口径）：三层**每一层**先**探测知识库是否已维护该层**——无则结合 KB + 用户给的业务信息**生成首版**（链路一次出全量；故事按每条链路依次；测试点按每条子链路的每个故事依次）；有则基于本次业务信息**判断是否需要更新**（故事层遍历每条子链路分链路推进）。每层的生成或更新都走「**设计 → 生成 → 评审 → 优化**」循环，评审完必须根据意见优化。
6. **首建/更新可混合、每层独立判定**：不存在"本项目处于首建阶段"这种全局开关（该逻辑已被用户否掉）。链路层更新 + 故事层更新 + 测试点层首建可在同一任务内共存；游标与过关状态按层独立记录。
7. **大纲是增量大纲**：只含本次任务涉及的链路/故事/测试点；首次生成时等于全量大纲。**人工审核通过后必须把三层增量维护回知识库**，保证 KB 与产品迭代对齐。
8. **制品归属** = **增量大纲留项目空间**（有的需求只涉及几条链路）；**进知识库的是对应完整产品业务的链路树 / 用户故事 / 测试点**。即 **KB = 全量真相（随产品迭代维护），项目空间 = 本次增量工作稿 + 评审痕迹**。
9. **业务信息入口** = 知识库 + 用户输入的业务文档。
10. **意见形态** = 结构化（对象 + 类型 + 要求动作），且对象类型必须支持 **"跨节点边界/接缝"** 这一类 target；修订必须交 **「意见落点对照表」**（每条意见 → 改了什么 / 为何未采纳）。意见**一次收齐、一批消化**，不逐条来回。
11. **失效传播** = 不自动标记（原 9c），但**人工发起的回溯/重算必须保留**——大纲门上人给的结构性意见要能回到对应层的环里重做、重新出大纲再审。
12. **接缝判据**（用户补的最锋利一条）：分块依次生成会出现 **"a 以为 b 覆盖了，b 以为 a 覆盖了"** 的漏测，块内自检看不见（每块内部都完整），必须站在全局视角评审。→ 全局审的落地形态 = **逐接缝审 + 一张共享实体矩阵收口**，不是"重看全量"；出口判据 **空归属 = 0**。
13. **走查 = 两次任务**：第一次拿首建 + 回写证据；第二次拿更新分支 + **增量 × 存量**接缝证据。走查的**输入源不预设**（合成业务文档或任一条真实产品线都可以），但两次的判据只依赖 KB 的能力面，不引用任何一条线的既有内容——**换一条产品线跑同一套环，除业务信息外无任何改动**才是"能力"的验收口径。
14. **修订轮次** = 层内无人审后需要可自动判的出口，但**意见不分等级：所有评审意见都必须被修订**（2026-10-05 裁定，覆盖控制方早稿的 blocking 分级 + 3 轮方案）；**每层硬上限 5 轮**，到上限带未消化项进大纲门由人裁决。
15. **测试点层有自己的一道全局审**（2026-10-05 复核确认）：= **实体 × 故事 点覆盖矩阵的空格核对**（§3③），不能用 ② 的声称核对代打——同一故事内的点互不为接缝，② 在点层必然空转。配套：点节点必须带 `entities` 与 `方向` 两个字段（§2），矩阵由账本确定性组装；判"这一格不需要点"**必须写业务理由**并随矩阵进大纲（§4）交人复核。大纲门的确定性一致性检查相应降为第四道 ④。
16. **任务范围描述符 = 运行时入口**（2026-10-05 追加）：用户指令归一化为 `{入口层, 目标子树, 终止层}`；**质量内核固定、任务范围可变**——任何写进 KB 的节点都必须经过其所在层的环 + 该层全局审 + 增量大纲人审门，指令只决定本次涉及哪些节点，不决定跳任何一道审。三道审**按范围缩、不按范围免**；**出口不缩**（窄任务同样产出 mini 增量大纲过唯一人审门）。**与「能力优先」（背景）的区分**：禁产物切片禁的是**能力范围**裁剪（只铺链路层这类），描述符是**单次任务范围**，内核仍必须能处理全树。**向上异议通道**：目标子树的上游本身应改时（如颗粒度错）不得静默只做子树，复用 §4 回溯回路交人裁决。
17. **计划制品与不收敛归因**（2026-10-05 追加；吸收 plan-and-execute 与 reflection 各一件，不套壳整范式）：① **计划 = 任务的第一个制品**——账本 `plan` 节 = 描述符 + 探测结果 + 每层首建/更新判定 + 块清单与顺序 + 预算；**确定性组装为主、LLM 只解歧义**；**重规划必须留痕**（触因：探测与指令预设冲突、结构意见要求跨块移动、轮次用尽、人审回溯；旧/新计划对照追加，不覆盖历史）。② **轮次用尽必须附「不收敛归因」**：业务信息不足 / 契约冲突 / 评审分歧 / 成本超限，四选一 + 一句说明，随未消化项进大纲门——否则"5 轮未果"与"5 轮摆烂"在人眼里无差别。**明确不吸收**：LLM 自由生成或改换工作流（重演裁定 16 的枚举爆炸）、自省式改进与自评分（见「业界标准形态对照」：无客观信号处的自评 = 假绿）。
18. **「空链路/空故事」的成立前提是层参与性，豁免必须可见**（2026-10-06 执行期追加，控制方裁定；用户可否决）：这两项检查问的是"本 run 是否要求该节点有下游"，而"哪些层进了本 run 窗口"是账本事实——`checks.py` 的契约是无 LLM、不读账本，故判据落在驱动侧过滤。**代价交换写明白**：豁免逻辑与检查逻辑分处两文件，后续给 ④ 新增"下游存在性"类检查的人必须同时来驱动登记。三条硬条件：**只丢这两类 code**（其余四项在下游被跳过时照报）、判据与范围计算**同源**、六项 hard code 计数口径不变；且被豁免的条目要进大纲的结构指标段（「hard 全部为 0」不许冒充「0 条被下游未进窗口豁免掉」——唯一人审门是本项目唯一的把关信号，静默丢弃等于拆门）。
19. **人审门的批准必须明示，待决不是批准**（2026-10-06 执行期追加，覆盖本片早稿"无意见即批准"口径；用户可否决）：回写是不可逆写，而"评审子没提取到意见"与"人说了通过"是两件事。出路三条——有意见→回溯重做 / 本轮原话**明示**批准→回写 / 两者都不是→本轮不做任何决定（零写入、状态维持待审、把待决转述给人），连续待决超过问询预算即**中止**。批准只认**本轮最后一条**人话，且全句含否定或延后标记即撤销授权（"不通过"里也含着"通过"）。失败方向统一偏保守：宁可多问一轮、宁可停住，也不猜一次授权去写库。
20. **图节点的 `config` 形参必须裸标注 `RunnableConfig`**（2026-10-06 执行期追加，计划文本缺陷的落点；用户可否决）：langgraph 按**注解类型白名单**决定要不要注入 config，而本仓模块一律有 `from __future__ import annotations`（注解以字符串比对），于是 `config: Any` 与 `config: RunnableConfig | None` 都被**静默跳过**——真图跑起来才缺参 TypeError，单测直调函数却全绿。凡新增图节点（driver/agent/gate/tools 及后来者）一律裸标注，不允许"宽化"。
21. **生产默认即进 loop，风险以走查兜而不以闸门遮**（2026-10-06 执行期追加；用户可否决）：`kb_enabled` 缺省 True 叠加裁定 A10 的激活判据 `bool(getattr(kb, "is_enabled", False))` ⇒ 线上 `case_design` 默认走专属 loop。reme 底座未就绪的窗口内，真实用户首见可能是「测试设计任务中止」的人话终帧而非旧 react 行为。判为 A10 冻结判据的**固有代价**（加 `is_started` 闸门要同时改 A10 与既有测试），故不改设计，改为**付费走查必须验两条**：① KB 就绪走通到 `awaiting_review`；② KB 未就绪/异常时终帧是人话而非栈崩。任一不达即在走查内提闸门修订。
22. **存量服务级测试必须显式注入 KB 替身**（2026-10-06 执行期追加；用户可否决）：`create_app` 缺省现装真 `RemeKbManager`，而 `is_enabled` 透射 `kb_enabled=True` ⇒ 本应测 react 的纯回合会被翻进 loop，且让存量测试依赖**真实 KB 对象**（违反"禁触真实知识库"纪律）。处置 = 在既有 `create_app` 调用处显式传 `_NoopKbManager`（纯 +6 行、零删除、断言原句在位），**不是放宽断言**。
23. **门禁读数一律以提交态为准，工作树读数须先排除并发在途件**（2026-10-06 执行期追加，纪律性裁定；用户可否决）：本项目允许多个代理在同一工作树并发（评审 + 实施），未跟踪的在途测试文件会让"全量红了"看起来像本任务的错。口径：以 `git archive <被审提交>` 解出的纯净树或提交态读数作门禁事实，脏树读数只作线索；并发进程改动一律**不回退、不认领**，如实记录。
24. **简报逐字与已发码冲突时以发码为准，冲突回填计划文本**（2026-10-06 执行期追加；用户可否决）：简报是从计划快照抽出的历史制品，实施代理若照抄过期文本就会改坏已发码。规则：不改已发码去迁就简报，改计划文本并挂裁定标记，账本留「简报历史制品不回改」的口径。
25. **复审回执不得顶掉处置说明——双文保留**（2026-10-06 执行期追加；用户可否决）：意见簿里人真正要读的是「改了什么」（主智能体处置说明），复审说明只是收敛证据。旧实现 `op["note"] = r.note or op["note"]` 把前者无条件抹掉，大纲的「意见落点对照表」因此只剩后者，属"按钮说谎"一类。改为一格并存：处置在前、回执以 `；复审：` 缀后；只有一文时用该文。销账判定与账本 schema 不动。
26. **多轮复审的全轨迹累积是特性，上界 `ROUND_CAP`**（2026-10-06 执行期追加；用户可否决）：同一意见最多缀 5 段 `；复审：`（块环轮次上界，且 plan 的预算由编排层确定性注入、模型抬不高）。实测最坏整行 156 字符（短回执）。裁决**保留全轨迹**——唯一人审门要看得懂"每轮谁说了什么、凭什么算已销账"；若日后嫌长，只在大纲渲染层加省略，账本仍留全量。
27. **回写续跑同样要再入授权，否定句绝不写库**（2026-10-06 执行期追加，裁定 19 的执行面补全；用户可否决）：`writeback_failed` 的续跑支路原先只按账本状态转场、**不读本轮人话**——实测「别写了，先停下」照样写库并落 `done`，把拒绝读成授权，且落在不可逆写路径上。修复把判据放在**唯一真正下笔的地方**（`h_writeback` 入口），一次覆盖两个入口（大纲门明示批准、失败续跑）；授权 = 无否定/延后标记 且（批准措辞 **或** 仅这条路合法的重试措辞）。重试词**不进**通用批准词表：在大纲门说一句「重试」不该触发一次不可逆写。未获授权时零写入、状态原样退回、终帧重申「回复『重试』再写」。
28. **处置侧同样不得顶掉既有轨迹——与裁定 25 对称**（2026-10-06 执行期追加；用户可否决）：裁定 25 只守住了「复审回执不覆盖处置说明」这一个方向。优化环的 `op["note"] = note or op["note"]` 留着反方向：同一条意见一旦被后续任一轮处置表带上说明（主智能体常把上一轮的 ref 一并重申），它此前累积的「处置＋复审」全轨迹就被最新那句整串顶掉，人看到的又只剩最后一次。改为新处置说明以 `；处置：` 缀在旧轨迹之后，只有一文时用该文；轨迹长度仍由 `ROUND_CAP` 有界（裁定 26）。销账判定与账本 schema 不动。

## 知识库侧外部前提（用户给定，本期按已具备设计，不做备选方案）

- **P-1 更新与删除**：`save_to_knowledge` 之外，KB 将提供节点级 **update / delete**。本期更新分支与回写分支直接建在这两项上。
- **P-2 按类型/桶枚举节点**：探测"这层有没有维护"、回写前定位既有节点、全局审的实体矩阵，都依赖**枚举**而非语义检索。现有 `_KB_JOBS` 白名单（`services/kb/config.py:32-93`）只有 status / list_knowledge_bases / knowledge_base_meta / **knowledge_search** / save_to_knowledge / reindex / index_update_loop / list_knowledge_inbox / promote_knowledge_inbox，**无按类型枚举**——需新增。
- **P-3 节点可寻址**：三层节点带**稳定类型标记、id、父引用**。本专项不假设任何产品线现有节点已带这三件；**探测时缺任一件即按"该层未维护"处理**（走首建分支），不做猜测性对齐或迁移。
- **P-4 新桶可被 reme 接受并纳入索引**：新增 `business/chains`、`business/stories`、`business/test_points`（或同族桶）后，`index_update_loop` 的 `watch_dirs` 靠启动期 `prepare_knowledge_startup` / `augment_jobs_for_knowledge` 追加发布桶（`services/kb/config.py:66-88`），需探针核实。
- **P-5 内容不感知 = 探测必须按类型枚举，不得用 top-k 语义检索**（这是产品线中立在实现上的唯一后果）：某条产品线 KB 里可能存在形态上极像用户故事或测试点的**历史遗留节点**（本专项不预设它们长什么样、有多少）；用语义检索判"这层有没有维护"必然假阳性，且会把旧命名空间的链接主动扩进上下文（`knowledge_search_step` 开着 `expand_links: True, max_links_per_direction: 10`，`services/kb/config.py:40-49`）。→ 探测、定位、去重、矩阵四类判定**一律走 P-2 的类型枚举 + P-3 的类型标记**；语义检索只用于"读业务信息"，不用于"判有无"。历史遗留节点本期**不作为已维护节点**，也不做迁移。
- **P-6 测试点颗粒度契约 = 本能力自己定义的产品线中立默认**（不从任何一条产品线的存量节点"吸收"）：**测试点最小单位 = 一个场景**（前置状态 + 一次触发动作），一次触发只产出一个测试点；**正向 / 负向 / 边界是断言方向，不是点数**，不强制各自独立成点。该契约写进提示词与 §2 的节点 schema，可由当次用户给的业务信息在**同一产品线内**收窄，不得由模型随手放宽。

## 设计

### 1. 阶段状态机

专属拓扑注册名 `case_design_loop`（`GRAPH_BUILDERS`，`orchestration/graph_registry.py:9`；`AgentSpec.graph_builder`，`agents/spec.py:14`），三层各自跑同一条**层内环**：

```
探测（按类型枚举，P-2）
  ├─ 未维护 → 首建分支：设计该层切分口径 → 分块生成 → 评审 → 优化 → 验收复审
  └─ 已维护 → 更新分支：判定本次业务信息是否触发更新 → 分块增量生成 → 评审 → 优化 → 验收复审
        ↓ 块全部收口
   该层全局审（§3 的 ①/②/③）→ 层内定稿 → 下一层
        ↓ 三层齐
   组装增量大纲 → 确定性一致性检查（§3 的 ④）→ 唯一人审门（§4）→ 回写（§5）
```

- **每层独立判定、允许混合**：三层各自的探测结果独立记录，同一任务内首建与更新共存是合法状态；不存在全局"首建开关"。
- **层内环的出口**：**评审意见不分等级——每一条都必须被修订**（2026-10-05 裁定，覆盖早稿的 blocking 分级形态）。一轮内意见**一次收齐**交主智能体，**优化后交回干净的评审子智能体复审**；复审仍出意见（含新出的）即进下一轮。每层硬上限 **5 轮**，到上限即带**未消化项清单**进大纲门由人裁决——**环的出口是"意见清零"或"轮次用尽"，不是"只剩非阻塞意见"**。未消化项清单的每条必须带**不收敛归因**（裁定 17）。
- **块（block）** = 一次生成的最小单位：链路层=整棵树一次出全量（首建）或受影响子树（更新）；故事层=一条子链路；测试点层=一条子链路下的一个故事。块的划分由主智能体按账本决定，**必须逐块留游标**。
- **游标与账本落文件**（对话只截最近 40 条，`services/chat.py:42`，装不下长期状态）：项目空间写工作稿目录 `design/`（账本 `design/ledger.json` + 三层草稿 + 大纲 `design/outline.md` + 意见归档 `design/reviews/`），每步重读、每步写回，中断续跑靠账本不靠记忆。**账本首节 = 计划（裁定 17）**：描述符 + 探测结果 + 各层首建/更新判定 + 块清单与顺序 + 预算；重规划以事件追加（触因 + 旧/新计划对照），不覆盖历史。
- **节点过关状态**写进索引：草稿 / 待审 / 已过审 / 失效待重算（轮数、意见归档指针、是否过审）。新需求来时才知道哪层可信。

**任务范围描述符（运行时入口，裁定 16）**：用户指令 → `{入口层, 目标子树, 终止层}`。例："针对链路 X 生成测试设计" = 入口=链路层（X 只做只读上下文）、目标=X 下全部故事与测试点、终止=测试点层。探测仍按裁定 6 在三层照跑，未涉及层判"本次不动"。

- **范围 = 影响闭包，不只是目标子树**：下闭包 + 上游只读上下文 + **横向接缝集**（同父兄弟边界、共享实体的跨枝故事）。① 的分母本就是业务信息来源，天然可缩到本次需求涉及的对象/角色/阶段；② 的"增量 × 存量"（§3②）在窄任务下即"本次子树 × 其余全量"；③ 的矩阵只填涉及的列，空格判据 = 本子树 story × entity 子矩阵 + 与未动链路的接缝。
- **命令词汇归一化**：指令拆成 {设计任务, 用例任务}——本期只做设计侧，跨到用例侧的指令只做设计部分并**明示边界**；"给链路 X 生成用例"且三层已过审无失效时，设计侧为空增量：过失效检查（裁定 11 口径）即移交下一片，不为"有产出"重生成。

### 2. 制品与数据形状

- **链路节点**：`type: chain`、`level`（1/2/…）、`id`、`parent`、名称、业务范围描述、不覆盖声明（明确排除项）。
- **故事节点**：`type: story`、`id`、`chains: [...]`（**多父即重复的合法表达**，对应裁定 2）、主角角色、业务前置、触发、期望结果、**假设清单**（见 §3②）。
- **测试点节点**：`type: point`、`id`、`story`、`场景`（前置状态 + 一次触发动作）、`entities: [...]`（**该点触碰的业务实体**——③ 的矩阵按这个字段组装，缺字段则矩阵无从生成）、`方向`（正向/负向/边界，**必填非空，但不占点数**，P-6）、优先级。
- **增量大纲**（项目空间，不进 KB）：本次涉及节点的**树形视图** + **本次计划表（描述符、块序、重规划事件）** + 每节点过关状态 + **未消化项清单（每条含不收敛归因）** + **重复标注清单** + **接缝归属表**。大纲是人审门的**唯一可视对象**，必须让人在一屏内看出"这次动了哪些、没动哪些、哪些存疑"。
- **结构化意见**：`{target: 节点id | "接缝(a,b)" | "树外遗漏" | "矩阵空格(实体,故事)", kind: 漏测/颗粒度/边界归属/命名漂移/失效, ask: 要求动作, evidence: 原文指针}`。**没有等级字段**——按裁定 14，每条意见都必须被消化或在落点对照表里给出"经核查已由 X 覆盖 / 本轮未消化"的去向。对象类型含接缝类与矩阵空格类是裁定 10 的硬要求：全局审出的意见通常是**新增一个承接节点或补一个点**而非改某块，没有这两类 target 则落点对照表无法表达。
- **意见落点对照表**：每条意见 → 改了什么 / 为何未采纳（含"经核查已由 X 覆盖"），是环的出口判据，也是大纲门上人的主要读物。

### 3. 全局评审：每层收口各一次，四道机制不同

放在"每次循环"不对（接缝判定需要两侧内容都存在，A 刚生成时 B 还是空的，审它只能靠猜）；只在大纲末尾审也不对（返工成本随时钟指数涨，且人审门就在眼前，退回极贵、实际几乎一定"将就过"——**等于在最容易造出假完整的位置设防**；末尾那次也没有资源再读业务信息来源做树外对照）。

**一道审只防它那一层的典型漏法**：① 防"整块业务没进树"，② 防"故事之间的接缝没人认领"，③ 防"故事之内的维度没铺开"。**②③ 不可合并**（2026-10-05 复核确认，把测试点层并进 ② 是错配）：同一故事内的点互不为接缝，声称表必为空，② 会直接通过 = 假全。

- **① 链路层收口 = 树外遗漏对照**（三层里唯一能查出"整块业务没进树"的一道，只能在链路层做）。两个只读子智能体：
  - **枚举器必须"盲于树"**：只拿业务信息来源（KB + 用户文档）列「业务对象 / 角色 / 阶段」清单，**不看已生成的链路树**——否则分母被树自身引导，必然假全。**"盲"是结构强制而非提示词叮嘱**：枚举器的任务简报与工具面里根本没有树；同一上下文里读过的东西撤不回，"先别看的禁令"也不可验证。
  - **对照器**：逐条问"这个对象/角色/阶段在树里落哪"，**无落点即出一条意见，按裁定 14 必须消化**。
  - 拆两个角色的第二条理由是**审计性**：盲枚举清单是独立制品，人能在大纲门上翻这张表追问"这行为什么没落点"，下次迭代还能复用同一分母做增量对照；合成一步则人只看到一个"通过"，分母怎么来的无从检查——违背"禁止把 AI 评审通过当质量证据"。
  - **诚实边界**：拆角色只买到视角独立，**买不到客观性**。枚举器自己漏列一整类对象时这道检查照样查不出，与"覆盖度无客观分母"是同一条限制，故唯一人类门不可撤。
- **② 故事层收口 = 声称核对**。每块生成时强制产出**假设清单**："我假设 X 场景由兄弟 Y 覆盖，我不覆盖"（首建期只能靠它——**不依赖任何产品线既有节点之间的链接字段**，见 P-5）。收口审的输入是**一张「声称 → 被声称方」对照表**而非全文，逐条去被声称方的实际认领范围验证；**声称存在但没人认领 = 空归属 = 出一条必须消化的意见**；仅可疑对才展开正文抽样。**跨片声称由主智能体配对后再派核对子任务**（主智能体只组装、不判断），表可按父分片并行审。
  - 更新模式下审的对象不只是增量内部，还必须覆盖 **增量 × KB 已有全量** 的接缝——否则本次新增枝会把老枝的空白"认领掉"却没人补（顺序污染）。
  - 四类接缝检查：同父兄弟的**边界归属**、**触发方/响应方配对**、**共享实体 × 枝的生命周期归属**（新建/改/删/失效/被消费每阶段至少一枝认领）、**颗粒度断层**（兄弟枝故事数悬殊是漏测指针）。
  - 与 ③ 的分工：② 只判**归属**（这个实体的这个阶段有没有枝认领）；③ 判**认领之后的兑现**（认领了却铺不出点）。同一实体在 ② 全绿、在 ③ 出一片空格，是合法且必须被查出的状态。
- **③ 测试点层收口 = 实体 × 故事 点覆盖矩阵的空格核对**。矩阵由账本**确定性组装**（点已带 `场景` 与 `涉及实体`，见 §2，组装不经 LLM），一个只读子智能体**只审这张表、不读点正文**：逐空格问"这一格真不需要点，还是漏了"——**需要但无点 = 出一条必须消化的意见**；判"不需要"**必须写业务理由**，理由随矩阵进大纲让人复核，**无理由空格 = 不通过**。成本与 ② 同级：审表不审正文，可按父分片并行。
- **④ 大纲门 = 跨层一致性 + 未消化项裁决**，**确定性检查、不用 LLM 子智能体**：父引用完整、无跳层、优先级沿树不违例、**未过审节点不得被下游引用**、剩余空归属数、矩阵无理由空格数、**每个点的断言方向字段非空**（P-6 的正/负/边界不占点数，但方向不许空——只作机器可校验的形状约束，不新增质量判据）、重复是否 100% 标注。子智能体在这里只做一个动作：把未消化项翻译成业务语言摘要给人。④ **不再负责找漏**。

成本：① 两个子任务 + ② 一个（可分片并行）+ ③ 一个（可分片并行，只读表）+ ④ 零 LLM。审的是表与一致性，不是全文。

判决权约束：**判决由评审子智能体出，主智能体不得改判**——只能引原文提事实性异议，异议交**另一个干净的子任务**裁决。每次评审都是**干净上下文**（不继承上一轮，避免自我确认）。

### 4. 大纲人审门（唯一人类门）

- 时机：三层定稿 + ④ 确定性检查通过后、**回写之前**。走现有三档权限与 gate（`auth_rules.py`），不新增门控件。
- 人看五样：**本次计划表**（描述符、块序、重规划事件）、增量大纲树形视图、④ 的结构指标与抽样（含**矩阵无理由空格清单与"不需要"的业务理由**、**断言方向缺失数**）、未消化项（**每条含不收敛归因**）与重复标注清单、落点对照表。
- 人给意见（一次收齐）→ 主智能体按 §5 优化 → 重新出大纲再审；结构性意见（"这两条链路该合并"）走**回溯回路**进对应层的环重做重审，不就地补丁。
- **批准必须是明示的**（裁定 19）：回写是不可逆写，"评审没提取到意见"不等于"人说了通过"。三条出路——有意见→回溯重做；本轮原话明示批准→回写；两者都不是→**本轮不做任何决定**（零写入、状态维持待审、把待决原样转述给人），连续待决到预算上限即**中止**而不是耗到某人随手一句话被当成批准。
- 本轮不采用自动失效标记（裁定 11），但**人工发起的重算必须能落到下游**：被改节点的后代在账本里标"失效待重算"，下次任务据此重跑。

### 5. 主 / 子智能体分工与工具面

- **主智能体**（`case_design`）：账本读写、块划分、生成、按意见**优化**、回写。优化时**按意见寻址做局部精读**（只读被指向的节点 + 其父与兄弟，不重读全文）——这是单写者可行的前提。
- **评审子智能体**：工具面**只读**（`read / grep_search / glob_search / web_search / knowledge_search`）→ 天然满足 `face_can_suspend`（`orchestration/auth_rules.py:51`）的可并行判据，多块可同时审；写权全部集中在主智能体。评审永远在子智能体、优化永远在主智能体，**两者不互换**。
- **优化后同一批意见必须交回一个干净的评审子智能体验收**（复审确认才算闭环）。
- **深度 1 结构锁不变**：子智能体注册表装配时不注入 `task`（`adapters/tools/__init__.py:45-46`），评审子不能再审别人。
- **出厂工具面**：`case_design` 的 `default_tool_ids`（`agents/catalog.py:24-`）补 `knowledge_search`、`save_to_knowledge`、`task`。事实澄清：KB 工具**不是** `kb_assistant` 专属——两件都在 `TOOL_CATALOG`（`services/capability_config.py:81,89`），`build_default_registry` 只要 `kb` 启用就对任何智能体注册（`adapters/tools/__init__.py:48-50`），缺的只是出厂默认与提示词口径。
- **回写的门禁口径**（读码纠正，勿再按直觉描述）：`save_to_knowledge` **确在执法集合**内（`auth_rules.py:42,48`），但 `free` 档一律不挂（:129）、`boundary` 档对 knowledge 直接放行（:131）——**回写确认由大纲人审门承担**，不另设权限档要求。

### 6. 拓扑与硬缝清单（不 honored 即静默失效）

- **gate 必须存在于每个会调工具的节点**。三档执法只挂在默认 react 图里（`agent_graph.py:176` `graph.add_node("gate", make_gate_node(...))`）；自定义拓扑若有节点绕过 gate 直接执行工具，第 5 片的边界执法对该智能体**零作用**。每个工具节点都要复刻 `agent → gate → tools` 的"未答调用"路由（`_unanswered` :57、`route_after_gate` :77）。
- **`GraphBuilder` 签名只有 `(provider, tools)`**（`agent_graph.py:29`），无阶段白名单 / 预算 / 项目上下文通道。**本期不改契约**：阶段与预算在 builder 内部按 tool name 分组自持；确需外置再单开一片。
- **事件折叠依赖节点名 `"tools"`**（`agent_graph.py:262` `payload.get("tools")`）与 `_round_no` 的 ToolMessage 计数（:80）——多阶段节点名不叫 `tools` 就收不到结果、round 会串。**自定义图的执行节点必须沿用 `tools` 命名**（或同步改折叠口径，本期选前者）。
- **末轮正文覆盖前轮**（`reply = str(payload["text"])` 的后写覆盖口径）：中间轮正文不落盘。所以三层**制品必须落文件**，不能只塞 messages；大纲、账本、意见表都以文件为真相，聊天只给指针与摘要。
- **provider 的 `tool_calls ⇔ ToolMessage` 双向配对不变量**：拓扑里任何改写/删除 tool_calls 的做法都会 400（第 5 片 P9 教训同型）。
- **`run_id == thread_id`、gate 重跑会重发 custom 帧**：前端按 `call_id` 幂等，专属 loop 不得新造帧语义；新增可见性走既有 `step`/`wait`/`draft` 口径，不扩事件类型。
- **`HISTORY_MAX = 40`**（`services/chat.py:42`）→ 长期状态一律文件，每步重读。

### 7. 命名与提示词（落地时改）

- `agents/catalog.py:27` 的 `desc` 与 `agents/prompts/case_design.md`（现 19 行，只有"产出统一用例表：编号/需求号/前置/步骤/预期/优先级"这套口径，含子智能体专项补的「委派」段）**缺链路/故事/测试点三层概念**，会把模型直接带成"一上来写用例表"——提示词按本文 §1–§5 重写：四层概念、两阶段视角、每层探测→首建/更新两分支、块划分与账本纪律、假设清单强制产出、优化寻址精读、回写只走大纲过审后。**「同步用例平台」按 2026-10-05 裁定从描述里删除**（本期不做平台对接，用例层也留下一片）。委派段保留并补"评审任务一律派子智能体、只读面可并行；优化自己做"。
- 提示词与账本里**不得出现任何一条产品线的具体业务名词或存量节点样例**；三层桶名与类型标记（P-4）作为**单点配置常量**定义，不散写进提示词——换一条产品线只换业务信息入口，提示词零改动。

## 验收

- **两次真机走查证据**：第一次 = 三层首建 → ①②③ 各出一次判决记录 → 大纲人审 → 回写 KB；第二次 = 已有三层 + 新业务信息 → 每层独立判定出现混合 → 大纲为增量 → **增量 × 存量**接缝有归属结论。
- **产品线中立证据（本专项的能力验收主项）**：两次走查**只用不同的业务信息输入**，代码/提示词/判据/桶配置零改动；若任一步骤需要引用某条线的既有内容才能通过，即判定为**能力缺口**，不判为"这条线特殊"。
- **结构闭合硬门禁（数字线，全部必须为 0）**：空链路（无故事）数、空故事（无测试点）数、无父引用节点数、跳层引用数、未过审节点被下游引用数、剩余空归属接缝数（②）、**矩阵无理由空格数（③）**、**断言方向缺失数（④）**、`entities` 缺失的点数（③ 的组装前提）、未标注的重复数（重复标注率必须 100%）。
- **环的有效性**：每层修订轮次 ≤ 5；**落点对照表必须覆盖当轮全部意见**（不分等级，不存在"非阻塞可搁置"这一档），每条都有去向（已改 / 经核查已由 X 覆盖 / 本轮未消化）；轮次用尽的任务必须把未消化项带进大纲门（不允许静默过）。
- **成本实测上限**：记录一次三层任务的真实调用数与 token，与讨论预估（一条 L2 枝 10~20 次、一条 L1 整枝上百次）对照；预估只随**规模**（节点数）变动、不随产品线变动，超预估 3 倍即停下报数 + 菜单，不擅自砍能力。

## 实施偏离登记（2026-10-05 拆计划期）

实施计划（`docs/superpowers/plans/2026-10-05-case-design-loop.md`）与本设计不一致处的落点登记；与本文冲突时以本节的计划口径为准。

1. **S1 工具面**：不把 `save_to_knowledge` 补进 `case_design` 出厂工具面（§5 原文「补 knowledge_search、save_to_knowledge、task」的第二项移除）。理由：`save_to_knowledge` 对未知桶静默回落到默认桶、节点 markdown 由模型拼装无法保证字段保真（type/id/parent 是 P-3 的地址面），且每次调用都是模型回合成本。回写改为驱动经 `KbClient` 确定性执行 `case_nodes_list / case_node_upsert / case_node_delete` 三件 job。
2. **A4 轮次口径**：裁定 14「每层硬上限 5 轮」落为：**每块**评审-优化环 ≤5 轮；**每层**全局审环（意见优化-复审）独立计数 ≤5；层内总轮 = 各块之和。
3. **A8 失效传播**：裁定 11 的「后代标失效待重算、下次任务重跑」落为最小诚实实现——人审回溯改动某层时，其**下游层全部**标 `stale_pending`（大纲展示、回写跳过）；**下次任务按 update 模式全块重跑**，不做增量子树推断。
4. **A10 激活判据**：`kb` 未注入或未启用（`getattr(kb, "is_enabled", False)`，**缺省 False**，与注册表闸门缺省 True 刻意不同）→ `case_env=None` → 驱动直通（等价 react）；`task_kind=case_only` 且无失效 → 空增量：明示边界后直接完成，不回写。
5. **A2 补充**：盲枚举的「结构强制」实现 = 驱动白名单清单（`design/manifests/sources.json` 只含 KB 业务桶与用户指定项目文件）+ 枚举简报不含树 + 工具面仅 read。
