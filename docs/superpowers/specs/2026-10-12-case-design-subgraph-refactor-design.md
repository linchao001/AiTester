# 用例设计智能体：子图化图架构（总览版）

> 本文档当前**只描述图架构**（有哪些子图、顶层如何连、按诉求如何路由），不含各子图内部流程、
> 依赖、状态续跑与测试等实现细节——那些在后续步骤逐个细化。方案通过以用户明确回复【方案通过】为准。

## 1. 重构目标（范式变化）

- 现状：一条 `START → driver → agent → gate → tools` 拓扑 + 一台 Python while 大状态机
  （`case_design/stages.py:drive_turn`）串起三层（链路/故事/测试点）+ 用例编写环 + 全局收口。
- 目标：改为**顶层编排图 + 多个子图**；顶层按用户诉求**智能路由**进入不同子图，每层/每类职责
  收进各自子图，子图之间以「制品 + 业务游标」衔接。
- 非任务的聊天子图用 langchain `create_agent` 产出；其余子图均为自定义 StateGraph。
- **移除 plan 环节**：原 `plan` 的判定依据（范围/模式探测/拆块/来源校验）都来自将被删除的旧代码逻辑，
  子图不再带独立的计划步。
- **完整重构（绿地设计）**：从本步起，后续方案按新需求设计，**不以现有 `stages.py` 等实现为约束**；
  旧实践预计大面积废除，节点划分/流程/状态均以新需求为准重新设计。

## 2. 子图清单

| # | 子图 | 产出方式 | 职责（一句话） |
|---|---|---|---|
| 1 | 聊天子图 | `create_agent` | 非任务只读问答，不落任何设计账本 |
| 2 | **业务链路专项子图** | 自定义子图 | 独立地创建/维护业务链路：自带 生成→评审→优化→全局审→大纲门→回写，只产链路（无计划步） |
| 3 | **用户故事&测试点专项子图** | 自定义子图 | 独立地按指定链路创建/维护其用户故事与测试点：内部自带 故事环 + 测试点环（各自的 生成→评审→优化→全局审→门→回写），不改链路本身（无计划步） |
| 4 | 链路层子图 | 自定义子图 | 需求用例设计专项的链路环节 |
| 5 | 故事层子图 | 自定义子图 | 用户故事环节 |
| 6 | 测试点层子图 | 自定义子图 | 测试点环节 |
| 7 | 用例层子图 | 自定义子图 | 用例编写环 + 末门 |

说明：专项子图（2、3）与需求用例设计专项的对应层子图（链路层 4、故事层 5、测试点层 6）都是
**完全独立**的（依用户决策）——专项入口只处理用户明确指定的范围（只建链路 / 按链路建故事&测试点），
需求用例设计专项入口自上而下串三层；两类专项共享底层确定性内核（校验/意见簿/评审驱动/预算/回写），避免逻辑复制。

## 3. 顶层图架构

```
        START ──▶ [router]（意图判定 + 续跑/新回合分流）
                        │
   ┌──────────┬─────────┼────────────────┬────────────────┬──────────────────┐
   ▼          ▼         ▼                ▼                ▼                  ▼
 [1 聊天]  [2 链路专项] [3 故事&测试点专项] [需求用例设计专项]  [按链路写用例]   (halt/人审等待
 create_   只建/改链路   按指定链路补故事+点  链路层→故事层→   缺口检查→选序列   按 ledger
 agent)                                  测试点层→门/回写                      续跑)
   │          │         │                │                │
   ▼          ▼         ▼                ▼                ▼
  END        END        END      (mixed)→[7 用例层]→END  齐备→[7 用例层]→END
                                                        缺→[3 故事&测试点专项]→[7 用例层]→END
```

- 顶层是**编排 + 路由**：`router` 只做意图判定与续跑分流，不产制品。
- 每个子图后接**条件边**：据业务游标决定「进入下一个子图 / 收口 END / 冒泡等待人审或 halt」。
- `大纲门 / 回写` 是跨层的全局收口节点（属需求用例设计专项），不单列为子图；不再有独立 plan 环节。

## 4. 五条主路由路径（按用户诉求智能判断）

1. **闲聊 / 非任务** → 聊天子图 → END。
2. **专项创建/维护业务链路**（诉求只针对链路本身）→ 业务链路专项子图 → END。
3. **专项按链路维护故事&测试点**（链路已明确，只想生成/维护该链路的故事与测试点，暂不做用例）
   → 用户故事&测试点专项子图（内部 故事环 → 测试点环）→ END。
4. **按需求做测试设计/写用例**（提供需求文档 + 知识库作业务信息，常涉多链路，完整链路）
   → 需求用例设计专项：`链路层 → 故事层 → 测试点层 →（大纲门 → 回写）→（mixed 需求）→ 用例层 → END`。
5. **按链路写用例**（业务链路已明确，用户指定某条链路要写用例）→ 能力缺口检查：
   - 该链路故事/点齐备且非陈旧 → 直接进 用例层子图（范围=该链路）；
   - 缺故事/点或陈旧 → 先走 用户故事&测试点专项子图 补齐 → 再进 用例层子图。

## 5. 子图间的连接契约（高层，后续细化）

- **制品衔接**：上游子图产出/回写的链路、故事、测试点节点（落 `design/` 与知识库）即下游子图的输入分母。
- **游标衔接**：仍保持**单一 durable owner** `design/ledger.json`（一个文件、一份 id 序列、一处回写协调），
  但账本内部**按任务分区游标**，以支持多专项任务交叉挂起/各自续跑：
  - 顶层放跨任务不变量：id 计数序列、`source_files`、任务登记表；
  - `tasks/<task_id>`：各自的 `{kind, 该子图专属游标, halt, awaiting_review, 回写节…}`（不同子图游标结构不同）。
  允许多个任务同时在办/各自停在人审门或 halt，互不覆盖；`router` 续跑时按 task 归属还原到对应子图。
  checkpointer 只保同一次 run 内的权限中断（跨回合业务进度仍靠 ledger）。
- **中断与人审门冒泡**：任一子图撞到权限中断（写/执行审批）或人审等待（大纲门/末门）时，
  以「本轮收口 + 落游标」的方式退出，下一新回合经 router 续跑回对应子图——沿用现耐久契约。

## 6. 业务链路专项子图（内部结构，逐个细化中）

入口先做**意图判定**，分出两条分支：

```
[链路专项子图] START
  │
  ▼
[意图判定]
  ├─ 全量新建 ─▶ 设计 →（评审 ⇄ 优化，迭代至合格链路树）→ 大纲门 ─┬─ 批准 ─▶ 回写 ─▶ END
  │                          ▲                                    │
  │                          └───── 提意见（转定向修正指令，回流重跑）◀┘
  └─ 维护更新 ─▶ 见下方「维护更新」流程
```

- **意图判定**：判断本次是「全量新建」还是「维护更新」（如：目标范围在知识库是否已有链路 + 用户诉求措辞）。
- **全量新建**：基于业务信息（知识库 + 用户提供）产出业务链路树；随后进入**合并后的单一质检环**
  （评审 ⇄ 优化，迭代到合格）——因链路层的块即整棵树，逐块评审与层全局审对象相同，故合并为一环，不再分设「全局审」。
- **大纲门（人审外环）**：质检环合格后，把链路树汇编成人类可读大纲并挂起等人审（中断、跨回合）：
  批准 → 回写；提意见 → 解析为定向修正指令**回流到质检环重跑** → 再次大纲门。
  即「质检环=机器认为合格，大纲门=人认可」，两者构成 `生成 ⇄ 人审` 的外层循环，直到批准才走回写。
- **回写**：批准后写入知识库的 `test/test_outline` 桶；产物为**一个 Markdown（.md）文件，汇总全部业务链路**
  （即整棵业务链路树），文件名体现该链路树，幂等覆写。（注：同一桶内还有「单链路 .md」文档，内容=该链路的故事+测试点，由故事&测试点专项维护，见 §7；链路树文档中每条链路条目会随故事维护同步。）
- **维护更新**：基于已有链路做增量维护，流程：

```
检测变更源（business 是否有更新 / 用户提供新需求信息）
  → 整理新业务信息
  → 分析受影响链路（链路级，产出「受影响链路集合」：每条受影响链路附加改动方向
    【更新 / 删除 / 新增】）→ 子任务复审 ⇄ 优化
    （复审双重校验：① 影响范围是否准确完整；② 每条链路的改动方向是否正确）
  → 逐条「受影响链路」按改动方向分派（分派动作不再设子任务复审，方向已经链路级集合复审把关）：
      更新 → 直接为链路改名（仅改名，不做链路内影响分析）
      新增 → 新增该链路设计（走新建流产出该链路）
      删除 → 标记移除该链路
  → 大纲门（人审门）─┬─ 批准 ─▶ 回写 ─▶ END
                     └─ 提意见 ─▶ 回到对应链路的「更新/新增/删除」步重跑
```

  要点：① 两级分析——先由链路级分析筛出「受影响链路集合」并**逐条标注改动方向
  （更新/删除/新增）**（未受影响的链路不动），逐条迭代只遍历该集合、按方向分派动作；
  ② 子任务复审只设一处——链路级「受影响链路集合」产出后（委派评审子），**既审范围
  准确性/完整性，也审每条链路的改动方向正确性**（错判方向 = 驳回并重判）；链路若存在
  实质性内容变化，在本复审判为「删除＋新增」组合方向；逐条分派后的更新/新增/删除三个
  动作**不再重复复审，也不做链路内影响分析**（「更新」仅改名，属确定性修改，链路改名
  的连带同步归回写步处理），优化按意见改；③ 人审门与全量新建同款外环，提意见只回流到
  对应链路的「更新/新增/删除」步（而非从头设计），批准才回写；④ 回写覆盖三类方向：
  更新=改名（链路树条目名与单链路 .md 文件名同步更名）、新增=追加链路条目、
  删除=从链路树汇总文档移除该链路条目（并同步处置其单链路 .md）。

## 7. 用户故事&测试点专项子图（内部结构）

以「指定链路」为锚，只生成/维护其**用户故事 + 测试点**，不改链路本身。入口做**意图判定**，分三支；
其中「全量新建 / 指定某条链路」为同一新建流程、仅**范围锚定**不同。关键区别：故事层、测试点层
都是**多块层**（故事按链路成块、测试点按故事成块），故各层质检**保留「逐块评审 + 层全局审」双环**
（链路专项的合并不适用于这里）。

**入口意图判定（先看触发来源，再定分支）**

- **承接业务链路专项子图（§6）**（入参=§6「受影响链路集合」的改动方向）→ **确定性映射，不再判意图**：
  链路新增 → **新建类**（指定某条链路支，锚定=新增链路）；
  链路更新（改名）→ **维护更新支**：改名即该链路的测试范围变化，须对其既有故事/测试点
  分析受影响范围并审查，逐条按【新增 / 更新 / 删除】动作方向分派；回写另含单链路 .md 随
  链路名同步更名；
  链路删除 → **维护更新支**：需**结合业务信息分析判断**该链路下的用户故事/测试点是否应删除，
  并**派子任务复查分析结论**；复查通过后按删除类动作处置故事/测试点，废弃单链路 .md、
  链路树移除其故事条目。
- **用户直接指定**（router 进入本子图）→ 按用户指令判断意图，走对应分支：目标链路尚无既有
  故事/测试点 → 新建类；已有且需增删改 → 维护更新支。

**新建类（全量新建 / 指定某条链路）**

```
[范围锚定] 全量新建=全部链路 / 指定某条链路=用户点名链路
  → 故事环：逐链路设计故事 → 逐块评审 ⇄ 优化 → 层全局审
  → 测试点环：逐故事设计测试点 → 逐块评审 ⇄ 优化 → 层全局审（覆盖矩阵）
  → 大纲门（人审外环）─┬─ 批准 ─▶ 回写 ─▶ END
                         └─ 提意见 ─▶ 按目标层回流：故事类→故事环、测试点类→测试点环
                                       （改故事会使其测试点陈旧 → 连带重跑测试点环）
```

**维护更新（增量）**

```
检测变更源（business 是否有更新 / 用户提供新需求信息 / 承接 §6 链路改名·删除）
  → 整理新业务信息
  → 定位受影响范围（受影响链路的每条故事/测试点标注动作方向【新增/更新/删除】；
     承接 §6 链路删除=结合业务信息分析判断其下故事/测试点是否应删除，结论同样进复审）
  → 子任务复审 ⇄ 优化（唯一复审点：审范围准确性/完整性 + 审每条动作方向正确性，
     含链路删除的「是否应删」分析结论，同 §6）
  → 逐条故事按动作分派（不再复审）：新增=设计故事 / 更新=修订故事 / 删除=废弃故事
  → 连带测试点按动作分派（不再复审）：对每个受影响故事（新增/更新）重估其测试点，
     同样按三类动作判定：新增=设计测试点 / 更新=修订测试点 / 删除=废弃测试点；
     故事删除→其测试点整体连带删除
  → 大纲门（人审外环）─┬─ 批准 ─▶ 回写 ─▶ END
                         └─ 提意见 ─▶ 回到对应故事/测试点的「新增/更新/删除」步重跑
```

要点：
- **承接 §6 改名的处理**：改名=测试范围变化，必须走故事/测试点的影响分析 + 复审 +
  新增/更新/删除逐条分派；单链路 .md 同步更名只是回写的附带动作，不能替代内容重估。
- **承接 §6 删除不默认整体废弃**：是否删该链路下的故事/测试点需结合业务信息分析判断，
  分析结论派子任务复查通过后才按删除类处置（含单链路 .md 废弃与链路树条目移除）。
- **子任务复审只设一处**（定位受影响范围后），既审范围也审每条动作方向；逐条分派的
  新增/更新/删除动作不再重复复审（与 §6 同款收敛）。
- **顺序依赖**：测试点派生自故事，所以故事环永远在测试点环之前；任一支线改故事都需连带重跑其测试点——**故事更新时，其测试点同样涉及新增/更新/删除三类动作**（不只是修订），故事删除则其测试点整体连带删除。
- **单个大纲门**覆盖故事+测试点交付，提意见按意见归属回流到对应环（非从头重跑）。
- **两级“分析”** 与维护链路同款：先定受影响范围，再逐项处理。
- **回写**：写入知识库 `test/test_outline` 桶；**一条链路一个 .md 文档，链路名即文档名**，
  文档内容=该链路的**用户故事 + 测试点**；同时把该链路的用户故事**同步更新到业务链路树文档**（§6 的汇总 .md）。

## 8. 需求用例设计专项（内部结构）

服务原始需求场景 1：给**需求文档/新需求信息** + 知识库作业务信息，常涉多链路，从需求一路做到用例。
入口做**意图判定**，判据只有一条：**目标需求是否交付过**（按需求名/范围映射认定既有设计制品/用例）——
无 → **全量新建**，有 → **迭代更新**。「链路/故事是否已存在」不参与意图判定，只决定从哪层开始执行
（两支通用，见「两支共同规则」）。专项入口一次判定、统一分派，各层子图不自判意图。
**全量新建**采用「逐层自审自写」：需求影响分析**融入链路层**、不再单设节点；每层自带人审门 + 回写，
各层以「影响集合」产出驱动下一层（与只含单层的 §6/§7 专项的区别在于 §8 由需求入口顺次串接三层并逐层交付）。
**迭代更新**保留「全局大纲门汇编 + 单次回写」收口。

**全量新建（新需求）——三层顺次新建（每层自审自写、以影响集合驱动下层）**

每层核心逻辑一致：分析本层影响集合 → 逐条判定新增/更新 → 子任务复审 → 新增+更新方案提交人审 ⇄ 优化
→ 人审通过回写 → 输出本层「影响集合」驱动下一层。

```
[需求用例设计专项] START（输入：需求文档 + 知识库）
  │
  ▼
[链路层]（含需求影响分析）
  分析需求影响链路 → 逐条判定：新增链路设计 / 更新现有链路 / 涉及未变（不处理）
  → 子任务复审 → 新增+更新方案提交人审 ⇄ 优化 → 人审通过 → 回写链路
  → 输出「影响链路集合」（= 相关链路清单：涉及未变 + 新增 + 更新）
  ▼
[故事层] 依「影响链路集合」逐链路：
  分析影响的用户故事 → 判定新增/更新 → 子任务复审 → 新增+更新方案提交人审 ⇄ 优化
  → 人审通过 → 回写故事 → 输出「影响用户故事集合」
  ▼
[测试点层] 依「影响用户故事集合」逐故事：
  分析影响的测试点 → 判定新增/更新 → 子任务复审 → 新增+更新方案提交人审 ⇄ 优化
  → 人审通过 → 回写测试点 → 输出「影响测试点集合」
  ▼
[mixed 判定] ─┬─ 含用例 ─▶ [用例层 §9·全量新建支]（入参=影响测试点集合）─▶ END
              └─ 纯设计 ─▶ END
  （任一层人审提意见 → 本层优化后重审；改上层连带下层重估重跑）
```

**迭代更新（同一需求再迭代）——从落点层往下逐层执行**

```
[迭代更新] START（输入：新增/变更需求信息 + 既有设计制品与用例）
  │
  ▼
[变更分析] 新需求 vs 既有大纲/用例 比对 → 「变更点」+「落点层」（变更触达的最高层）→ 子任务复审
  ▼
自落点层往下逐层执行（未触达的上游层原样复用、跳过）：
  [链路层] → [故事层] → [测试点层]
  各层逐对象：定位受影响集 → 子任务复审 ⇄ 优化 → 更新（新增对象走新建流）；
  链路层产出同为「相关链路清单」（涉及未变+新增+更新）
  ▼
[全局大纲门] 汇编实际执行层的变更 → 人审（中断/跨回合）
  ─┬─ 批准 ─▶ [回写 test_outline] ─▶ mixed 判定 ─┬─ 含用例 ─▶ [用例层 §9·维护更新支] ─▶ END
   │                                              └─ 纯设计 ─▶ END
   └─ 提意见 ─▶ 回流到目标层的「更新」步（连带下游陈旧重跑）
```

**两支共同规则**（规则集中于此，两支图内不再重复标注）：
- **可从低层起执行**：需求命中的链路/故事已存在且无需结构改动 → 该层原样复用、跳过。最常见即
  「链路/故事不动，只在既有故事下增测试点、补用例」——全量新建从测试点层起走**新建流**
  （终点接 §9 新建支），迭代从测试点层起走**更新流**（终点接 §9 维护更新支）。
- **链路层工作与产出**：需求影响分析融入链路层首步；工作仅两类——**新增链路设计** / **现有链路维护**（+涉及未变不处理）；产出为**本需求影响链路集合**
  （= 相关链路清单：涉及未变 + 新增 + 更新），作为故事层的范围分母（衔接 §5 制品衔接）。
- **逐层递进定位**：入口分析只定最高层范围（链路集合 / 落点层），其后故事/测试点层各自再逐对象
  定位受影响范围，每层定位都过一次子任务复审（复用 §6/§7 「定位受影响范围→子任务复审」原则）。
- **顺序固定、连带只对下游**：链路 → 故事 → 测试点不可颠倒；改链路→其故事/测试点/用例重估，
  改故事→其测试点/用例重估；未触达的上游层不进质检环。
- **逐层自审自写 / 逐层交付**（全量新建）：每层「子任务复审 + 本层人审门 ⇄ 优化 + 回写」，并以「影响集合」驱动下一层；不再单设需求影响分析节点、不在末尾汇总全局大纲门。
- **迭代更新收口**：各层跑设计+质检环，末尾统一走**单一全局大纲门 + 单次回写**汇编实际执行层变更。
- 各层人审门/全局大纲门与用例层末门均为**独立人审环**；mixed 是否续跑用例层由需求决定，用例层进哪支由**对应测试点有无对应用例**决定（无→新建支，有→维护更新支）。

## 9. 用例层子图（内部结构）

用例层是设计（链路/故事/测试点）的**下游**：**依据测试大纲（测试点）编写用例**——重点是「编写 + 评审到合规」，不是「设计」。可由需求用例设计专项（mixed）
或「按链路写用例」进入；范围 = 测试大纲（测试点）。入口同样做**意图判定**（全量新建 / 维护更新，同 §6/§7）。

```
[用例层子图] START（输入：测试大纲（测试点）+ 业务信息）
  │
  ▼
[意图判定]
  ├─ 全量新建 ─▶ 按测试大纲 逐链路 → 逐用户故事 分批（一个用户故事 = 一个编写批次任务；
  │              范围已由大纲标注，仅确定性切块）
  │              → 逐批质检环（批内两阶段）：
  │                 ① 逐条编写 + 逐条质检 ⇄ 优化（每条用例依次质检，重点：用例规范）
  │                 ② 批次完成后，对该用户故事的全部用例做全局质检 ⇄ 优化（重点：与大纲的覆盖度，可多不可少）
  │              → 所有批次完成后 → 末门（大纲门）─┬─ 批准 ─▶ 回写 ─▶ END
  │                                                 └─ 提意见 ─▶ 回流到相关批次质检环重跑
  └─ 维护更新 ─▶ 检测变更源（大纲变化 / 业务更新 / 用户新需求）
                 → 定位受影响用例 → 子任务复审
                 → 逐条「受影响用例」：分析影响 → 子任务复审 ⇄ 优化 → 更新用例
                 → 末门（大纲门）─┬─ 批准 ─▶ 回写 ─▶ END
                                   └─ 提意见 ─▶ 回到「更新用例」步重跑
```

要点：
- **两支意图的区别**：全量新建=大纲里的测试点**尚无对应用例**，整批从头编写；维护更新=已有用例，因**大纲/业务变更**使部分用例过时/需增删改，只动受影响集合（未受影响用例不动），且提意见仅回流到「更新用例」步（同 §6/§7）。
- **批次粒度=一个用户故事**：编写按 **逐链路 → 逐用户故事** 推进，**一个用户故事即一个编写批次任务**（对应其测试点范围），控单批规模。
- **批内双阶段质检（取代「逐块评审 + 层全局审」双环）**：
  ① **逐条质检**——批次内每条用例编写完成后**依次单独质检 ⇄ 优化**，重点是**用例规范**（结构/字段/步骤/预期等符合编写规范），问题在当条修复、不留到批尾；
  ② **故事级全局质检**——该批次全部用例逐条质检通过后，对**这一用户故事的所有用例**整体质检 ⇄ 优化，重点是**与大纲的覆盖度**（大纲里该故事的每个测试点都必须有对应用例=不可少硬约束；允许额外用例=可多，不判违规）。
  覆盖度已在故事级核验（大纲按故事分层标注，各批次之和即全大纲），故**不再另设层全局审**；两阶段分别对应「内容规范」「范围符合」双目标，不再合并审。
- **范围来自大纲、不重判**：全量新建的用例范围就是测试大纲里的测试点，只需按 链路/用户故事 确定性切块控规模；只有**维护更新**才需「定位受影响用例」（既有用例↔变更点的映射，大纲给不出），并过子任务复审。
- **末门**与其他层大纲门同款人审外环；提意见按意见归属回流到**相关批次**的质检环（规范类→该批逐条质检、覆盖类→该批全局质检），不从头重跑；回写落库桶/命名待定（用例文档，先占位）。

## 10. Router 意图判据（顶层路由细化）

`router` 是确定性入口节点（不产制品），只负责「续跑分流 + 新任务意图判定」。输入：用户消息 + ledger。

```
[router] START
  │
  ▼
① 续跑优先：ledger 是否有挂起任务（awaiting_review / halt）？
  ├─ 有，且本消息是其回应（批准/提意见/继续）→ 绑定该 task → 续跑到对应子图/收口节点
  │     （多个挂起：按用户指明 / 最近一次 / 适情澄清 确定归属）
  └─ 无 → 进入 ② 新任务意图判定
  ▼
② 新任务意图判定（四信号：输入形态 / 诉求动词 / 目标对象 / 范围）→ 五选一：
  ├─ 闲聊 / 非任务 / 判不准 → [聊天子图]（只读、不落账本）
  ├─ 只要建/改业务链路 → [链路专项子图 §6]
  ├─ 按指定链路建/改故事&测试点 → [故事&测试点专项子图 §7]
  ├─ 给需求文档、涉多链路、做到用例 → [需求用例设计专项 §8]
  └─ 指定链路写用例 → 缺口检查 → 齐则 [用例层 §9]；缺则先 [§7] 补齐再 [§9]
```

判定信号与原则：
- **输入形态**：有无需求文档（有→倾向 §8）；有无指定链路（有→倾向 §7/§9）。
- **需求类统一进 §8**：新需求 vs 同一需求迭代不由 router 区分，由 §8 入口意图判定（目标需求已有设计制品/用例→迭代更新支）。
- **目标对象**：用户想交付什么（链路 / 故事&测试点 / 用例）。
- **续跑优先于新分类**：先排查挂起任务，避免把“对大纲门的回应”误判为新任务。
- **判不准时保守**：倾向走只读聊天子图并澄清，不轻意误起任务、不污染账本。
- （可选）意图判定低置信度时可轻量确认；路由可逆，不强制子任务复审。

## 11. 聊天子图（create_agent）

七个子图中**唯一**用 langchain `create_agent` 产出的子图；服务非任务的只读问答。

```
[聊天子图] START → create_agent(model=只读绑定的 LLM shim, tools=只读工具面, prompt=聊天指令)
  → agent ⇄ tools 循环（只读：浏览/检索/知识库召回/只读命令）
  → 自然收束 → END
```

要点：
- **只读工具面**：仅放浏览/检索/`knowledge_base_recall`/只读命令；写、编辑、`save_to_knowledge`、`run_python_script`、`pwsh` 等写/执行类工具一律禁用。
- **零副作用**：不读写 `design/ledger`、不写文件、不落任何设计账本（对应 router 的“判不准时保守走聊天”）。
- **无门无回写**：非任务模式，不进大纲门/不回写；工具全只读，无需权限 gate。
- **迭代上限**：映射到子图 `recursion_limit`，触顶给收尾文案。
- **计量/帧口径**：模型入参用一个包住现有计量 provider 的 `BaseChatModel` shim，不绕过计量与流式帧（属工程落地项，见 §12）。

## 12. 跨子图机制（状态 / 续跑 / 人审门 / 权限中断）

两类中断 + 一个统一收口约定，贯穿所有子图：

- **权限中断（写/执行审批）**：子图内的 gate 节点用 `interrupt()` 挂起（写盘/执行前审批）。
  子图作为节点挂载时**共享同一 checkpointer + thread**，故 `interrupt()` 可跨嵌套子图挂起/续跑。
- **人审门（大纲门/末门）**：以 `awaiting_review` 本轮挂起，等用户下一条消息（批准/提意见）；跨回合。
- **冒泡式收口**：任一子图撞到上述两类之一，以「本轮收口 + 落游标」退出到顶层 END；
  下一新回合经 `router`（§10）读 ledger 定位归属 task → 重新进入对应子图续跑。
- **durable 边界（接 §5）**：跨回合业务进度（游标/ halt / awaiting_review / 回写节）只存 `design/ledger.json` 的
  `tasks/<task_id>`；checkpointer 只保同一次 run 内的权限中断，不存跨回合理由。
